# DECISIONS

## 2026-08-11 개발 요청의 기본 외부 배포 범위

- 이후 FLICK의 개발 진행 요청은 사용자가 배포 제외를 명시하지 않는 한 집중 검증, 기존 GitHub `main` 푸시, 기존 EAS Hosting `beta` 별칭 배포와 외부 모바일 QA까지 포함한다.
- 새로운 저장소·호스팅 대상·유료 플랜은 자동 생성하거나 전환하지 않는다. 과금이 필요하거나 기존 승인 대상에 접근할 수 없으면 배포 전에 멈추고 알린다.

## 2026-08-11 5D 설명 가능한 개인화

- 취향 유형은 완료 기록이 3편 이상일 때만 제시한다. 그 전에는 필요한 기록 수를 알려주며 단정적인 문구를 사용하지 않는다.
- 분석 입력은 사용자가 선택한 키워드·Light 질문 태그·별점·기록 방식·감상 시점으로 제한한다. 리뷰 본문과 신규 AI 호출은 사용하지 않는다.
- 유형·반복 패턴·다시보기·취향 밖 추천은 같은 입력에 같은 결과를 내는 결정 규칙으로 계산하고 사용자에게 근거를 함께 표시한다.
- 사용자는 개인화 결과를 숨기고 다시 켤 수 있다. 숨김은 기록을 삭제하지 않으며 기기별 설정으로 저장한다.

## 2026-08-11 5E 제한된 참여형 실험

- 첫 실험은 운영자가 고정한 영화 퀴즈와 단일 선택 투표로 제한한다. 범용 게시물 에디터와 자유 텍스트 AI 생성은 포함하지 않는다.
- 퀴즈 정답은 클라이언트 응답에 포함하지 않고 서버 RPC가 판정한다. 사용자별 최대 3회 시도와 히든 블록 해금을 서버 상태로 보존한다.
- 투표는 사용자·투표당 첫 응답 1회만 허용하고 이후 변경을 거부한다. 결과 집계만 인증 사용자에게 RPC로 제공한다.
- 네 원본 테이블은 `anon`, `authenticated` 역할에 직접 개방하지 않는다. 5E는 Supabase 무료 베타 범위를 벗어나는 신규 과금 요소를 사용하지 않는다.

## 2026-08-11 5C 랭킹과 편집 큐레이션

- 랭킹은 초 단위 실시간이 아니라 Super Admin이 갱신하는 최근 7일 스냅샷으로 제공한다. 공개 완료 리뷰가 5건 미만이면 순위를 만들지 않고 표본 부족 상태를 설명한다.
- 영화 순위는 기간 내 공개 완료 리뷰 수, 키워드 순위는 리뷰 키워드와 Light 질문별 선택 태그를 집계한다. 비공개·초안·본문은 집계 대상이 아니다.
- 스냅샷은 최근 12회만 보존하고 운영 갱신 행위를 감사 로그에 남긴다. 현재 베타 규모에서 별도 스케줄러와 추가 과금을 만들지 않는다.
- 감정 기반 추천은 기존 결정적 추천을 명시적 탐색 진입점으로 확장하며 카드에 이유를 표시한다. AI 호출이나 신규 과금은 사용하지 않는다.
- 니치 큐레이션은 운영자가 직접 제목·설명·영화·선정 이유를 편집한다. 전문가 큐레이션은 실제 작성자, HTTP(S) 원문 출처, 게시 권한 확인이 없으면 서버가 공개를 거부한다.
- 랭킹·큐레이션 테이블은 클라이언트 역할에 직접 열지 않고 인증 사용자 공개 조회 RPC와 Super Admin 변경 RPC로 분리한다.

## 2026-08-11 5B 최소 피드와 사용자 컬렉션

- 홈은 기존 취향 영화 추천을 유지하면서 공개 Light 리뷰, Core 매거진, 공개 컬렉션을 각각 별도 섹션으로 제공한다.
- Light는 빠른 공감과 댓글 진입을 우선하고, Core는 긴 문장 가독성과 공감·저장을 우선하는 카드 형태를 사용한다.
- 컬렉션은 계정 소유 데이터이며 기본값은 `private`이다. 공개 컬렉션만 다른 인증 사용자가 조회·저장할 수 있다.
- 컬렉션당 영화는 중복 없이 최대 100편으로 제한한다. 컬렉션에서 제외해도 영화 캐시와 사용자의 감상 기록은 삭제하지 않는다.
- 컬렉션 원본 테이블은 클라이언트 역할에 직접 개방하지 않고 소유권과 공개 상태를 확인하는 `security definer` RPC로만 접근한다.
- 팔로우·알림·무한 스크롤·실시간 랭킹은 5B에서 제외하고 실제 공개 콘텐츠가 쌓인 뒤 5C에서 판단한다.

## 2026-08-11 5A 공개 콘텐츠 기반

- 공개 기록 본문 소유권은 계속 작성자에게만 둔다. 다른 인증 사용자는 별도 RPC를 통해 공감·저장·댓글·신고만 수행한다.
- 좋아요와 저장은 사용자·기록당 1건으로 제한하고 반복 요청은 같은 상태로 수렴한다.
- 댓글은 500자, 한 단계 답글까지만 허용한다. 본인 삭제는 답글 문맥을 보존하기 위해 본문을 비우고 삭제 상태를 남긴다.
- 신고는 사용자·기록당 1건을 갱신하는 방식으로 중복을 막는다. 관리자는 기존 `can_moderate_reviews` 권한이 있을 때 기각 또는 비공개 전환만 수행한다.
- 커뮤니티 테이블은 인증 역할에도 직접 열지 않는다. 모든 작업은 공개 완료 상태·현재 사용자·개별 권한을 다시 확인하는 서버 RPC로 수행한다.
- 전환 측정은 사용자 ID·이메일·댓글·리뷰 본문을 저장하지 않고 기기별 임의 세션 ID, 허용된 이벤트명과 `surface/mode/source`만 저장한다. 측정 실패는 제품 흐름을 막지 않는다.
- 5A는 기존 공개 상세에 상호작용을 연결해 수직 검증하고, 여러 기록을 모아 보여주는 피드 화면은 5B에 구현한다.

## 2026-08-11 차기 기능 개발 순서

- 디자이너의 기능 배치표는 화면 구현 순서로 사용하지 않고, `데이터 기반 → 읽기 피드 → 집계·큐레이션 → 개인화 → 실험` 순서로 개발한다.
- 공개 피드와 좋아요·댓글·저장 계약을 랭킹보다 먼저 만든다. 랭킹이 실제 사용자 행동을 집계해야 콜드스타트와 조작을 통제할 수 있기 때문이다.
- 실시간 랭킹의 첫 버전은 초 단위가 아니라 최근 7일 기준 주기 집계로 정의한다.
- 통합 기록 관리, 감정 기반 큐레이션, Light/Core 기본 리포트는 이미 존재하므로 신규 구축 대신 5단계 기능에 맞게 확장한다.
- 니치·전문가 큐레이션은 관리자 수동 등록으로 먼저 검증한다. AI 자동 생성과 전문가를 가장한 콘텐츠는 사용하지 않는다.
- 취향 유형과 추천은 최소 데이터 기준과 설명 가능한 규칙을 먼저 사용한다. 자유 텍스트 AI 분석은 명시적 동의·비용 상한·캐시 정책 확정 전까지 후순위로 둔다.
- 미니게임과 인터랙티브 게시물은 핵심 재방문 루프가 검증된 뒤 제한된 형식으로 실험한다.

## 2026-08-10 슈퍼 관리자 권한 모델

- 운영 계정은 소스 코드의 이메일 목록이 아니라 `admin_access`의 서버 검증 역할로 식별한다. 최초 지정은 운영 Supabase에서 기존 인증 사용자를 찾아 수행하며 개인 이메일은 Git에 남기지 않는다.
- 초기 권한은 사용자 조회와 기록 조회만 허용한다. 기록 비공개 전환과 영구 삭제는 각각 독립된 스위치로 필요한 동안만 활성화한다.
- 관리자의 `수정`은 사용자 작성문을 대신 고치는 기능이 아니라 공개 기록을 비공개로 전환하는 운영 조치로 제한한다. 비밀번호 열람, 사용자 로그인 대행, 사용자 계정 삭제는 제공하지 않는다.
- 관리자 화면 표시와 실제 데이터 접근은 분리한다. 모든 조회·변경·삭제는 `security definer` RPC가 현재 계정과 개별 권한을 다시 검사하며, 기반 테이블은 클라이언트에 직접 개방하지 않는다.
- 사용자·기록 조회, 권한 변경, 비공개 전환, 삭제는 관리자 감사 로그에 남긴다. 삭제된 본문 원문은 로그에 복제하지 않는다.

## 2026-08-10 이메일·비밀번호 계정 전환

- 반복 Magic Link 대신 Supabase Auth의 이메일·비밀번호 회원가입/로그인을 기본으로 사용한다. 비밀번호 원문이나 해시는 public CRUD 테이블에 직접 저장하지 않는다.
- 가입 시 닉네임(2~20자)을 받고 `profiles.display_name`에 저장한다. 닉네임은 현재 표시 이름이며 전역 고유 사용자 ID로 취급하지 않는다.
- 이메일 소유 확인은 첫 가입 때 1회 유지한다. 이후 일반 로그인에는 이메일 발송이 필요하지 않다.
- 기존 Magic Link 사용자는 같은 이메일의 비밀번호 재설정 링크로 비밀번호를 만든 뒤 기존 계정과 기록을 계속 사용한다.
- 마이 화면에서 닉네임과 비밀번호를 바꿀 수 있고 기존 내보내기·계정 삭제·RLS 권한은 유지한다.

## 2026-08-07 웹 우선 전환

- 첫 출시 우선순위를 앱스토어 배포가 아닌 모바일 반응형 웹/PWA로 변경한다.
- Expo와 Expo Router의 공통 코드베이스는 유지해 향후 iOS 앱 전환 가능성을 보존한다.
- 1단계 완료 조건에서 Apple 로그인과 iOS 빌드를 제외하고, Supabase 이메일 로그인·데이터 저장·모바일 웹 검증을 포함한다.
- 신규 Supabase 프로젝트는 클라이언트에서 publishable key를 사용하고 secret/service-role key는 사용하지 않는다.

## 결정

- Focus Quest와 분리된 `C:\Users\letsh\Documents\Click`를 신규 서비스 기획 루트로 사용한다.
- 물리 폴더는 안전하게 `Click`으로 유지하고 표시 이름은 작업명 `FLICK`를 사용한다.
- 제품의 중심은 영화 정보 탐색이 아니라 감정 기반 발견과 감상 기록의 반복 루프다.
- 초기 MVP는 개인 기록 가치 검증에 집중하고 공개 커뮤니티는 후순위로 둔다.
- AI는 사용자 글을 대체하지 않고 질문, 키워드 정리, 초안을 보조한다.
- Light와 Core를 상황에 따라 선택하는 두 기록 모드로 정의한다.
- 취향 리포트 1차 버전을 MVP의 핵심 보상 화면에 포함한다.
- 북극성 지표는 월간 의미 있는 감상 기록 완료 수로 둔다.
- 플랫폼 우선순위는 iOS 앱 → 반응형 웹 → Android 앱으로 둔다.
- 개발 언어는 TypeScript, 앱·웹 프레임워크는 React Native + Expo + Expo Router로 정한다.
- 백엔드의 초기 선택은 Supabase이며 DB·Auth·Storage·Edge Functions를 사용한다.
- 영화와 AI 외부 서비스는 서버 어댑터 뒤에 두어 공급자를 교체할 수 있게 한다.
- 1단계 구현은 Expo SDK 57 안정 버전과 npm lockfile을 사용한다.
- 인증 세션은 네이티브에서 SecureStore, 웹에서 AsyncStorage에 저장한다.
- Supabase 환경이 없을 때는 외부 전송 없는 기기 내 데모 모드로 온보딩을 검증한다.
- 실제 로그인 데이터는 Supabase RLS 정책과 서버 migration을 적용한 뒤 저장한다.
- 영화 공급자는 TMDB로 정하고 앱은 Edge Function만 호출한다. 공급자 토큰은 서버 비밀값으로만 둔다.
- 검색·추천은 Supabase 영화 캐시를 우선 복구 경로로 사용하며, 보고 싶어요는 사용자별 RLS가 적용된 `watchlist`에 저장한다.
- TMDB 필수 고지는 Credits 화면에 항상 노출한다.
- TMDB의 공급자 데이터는 안정적인 내부 영화 UUID와 분리한다. 상세정보를 다시 받거나 작품이 공급자에서 비활성화되어도 `watchlist`와 향후 리뷰·감상 기록의 영화 참조는 유지한다.
- 2.5단계는 공식 일일 ID 내보내기를 경량 색인 후보로 사용하고, 출연진·OTT·이미지·번역 등 전체 상세는 사용자가 작품을 열 때 Edge Function이 받아 별도 캐시한다.
- 상세 응답의 원본도 서버 캐시에 보존하고 `complete`, `source_incomplete`, `failed` 상태를 기록해 공급자 원본부터 비어 있는 항목과 수집 실패를 구분한다.
- Free DB 500MB에서 116만 편 전체 색인의 예상 사용량이 약 282MB이므로 실제 일괄 적재는 보류한다. Free 플랜은 자동 과금되지 않지만 한도 초과 시 DB가 읽기 전용이 될 수 있다.
- 외부 사용자 테스트는 Expo Free의 EAS Hosting Preview URL로 먼저 진행한다. 주소를 아는 사람은 누구나 열 수 있으며 별도의 접근 암호는 제공하지 않는다.
- 3A·3B 기록의 최종 원본은 Supabase이며 미완성 입력만 기기에 복구본으로 둔다. 완료 기록은 기본 비공개이고 본인 RLS를 강제한다.
- Light는 빠른 감정 기록, Core는 요소별 성찰에 맞춘다. 개별 질문은 선택 사항이지만 완료 시 별점과 최소한의 의미 있는 입력을 검증한다.
- AI와 음성 입력은 3C로 분리해 수동 기록 흐름을 먼저 완성하고, AI 장애나 비용 정책이 핵심 기록 저장을 막지 않게 한다.
- 3C의 질문·태그 단계는 AI 없이 동작한다. 제목·장르·감독·주요 출연진에 기반한 결정적 규칙으로 영화별 질문 5개를 구성하고 정보가 부족하면 제목 기반 안전 질문으로 대체한다.
- Light 질문은 한 장씩 진행하며 질문당 최대 3개 태그, 건너뛰기, 최소 3문항 완료 규칙을 사용한다. 질문 문구와 선택지는 리뷰에 스냅샷으로 보관해 생성 규칙이 바뀌어도 과거 기록을 유지한다.
- 같은 질문의 선택 태그는 AI용 입력이 아니라 현재부터 독립적인 사용자 기록 데이터다. 향후 AI 초안은 이 데이터를 읽기만 하며 사용자 승인 전 최종 기록을 덮어쓰지 않는다.
- 완료 기록의 공개 범위는 `private`과 `public` 두 가지로 제한한다. 친구 관계 모델이 없으므로 친구 공개는 제외하며, `public`은 익명 인터넷 전체가 아니라 로그인한 Flick 사용자에게만 읽기를 허용한다. 초안은 선택값과 무관하게 항상 비공개다.
- Core는 영화별 Q1을 메타데이터로 만들고, 각 답변을 받은 뒤 Gemini가 이전 질문·답변과 연결된 다음 질문을 생성해 Q5까지 진행한다. 이전 답변을 수정하면 뒤 질문과 답변을 폐기하고 다시 생성해 흐름의 일관성을 유지한다.
- Gemini 무료 등급은 성인 내부 테스트에만 사용한다. 개인정보·민감정보 입력을 금지하고 사용자가 명시적으로 동의해야 첫 AI 호출을 허용한다. 오류나 무료 할당량 초과 시 안전 질문으로 전환하며 기록 저장은 계속 가능하다.
- Gemini 키는 Supabase Edge Function 비밀값으로만 보관한다. Google Cloud `Klick` 프로젝트에는 결제 계정을 연결하지 않아 유료 청구 경로를 열지 않는다.
- Core AI 리뷰 초안은 Q1~Q5에 각 20자 이상 답한 뒤 별도 동의와 사용자 버튼 입력으로만 생성한다. 다섯 Q/A에서 키워드 3~5개와 편집 가능한 초안을 만들되 자동 완료·공개하지 않는다.
- 자유 감상에 사용자가 작성하거나 수정한 내용이 있으면 AI 재생성 전에 명시적인 교체 확인을 받는다. 생성 실패·무료 한도 초과 시 기존 본문과 질문 답변을 그대로 유지한다.
- 기록 완료 검증은 감상일, 별점, Light 최소 3문항 태그 또는 Core Q1~Q5 각 20자 답변만 필수로 본다. 누락 시 최초 실패 영역으로 자동 스크롤하고 해당 영역과 완료 버튼 아래에 구체적인 완료 조건을 표시한다. AI 동의·AI 초안·감정 키워드·공개 범위는 선택 기능으로 유지한다.
- Core 연계 질문은 사용자당 하루 20회·분당 6회, 리뷰 초안은 하루 5회·분당 2회로 서버에서 원자적으로 제한한다. 한도 초과는 유료 호출로 전환하지 않는다.
- 이메일·한국 휴대전화·주민등록번호 패턴은 Gemini 전송 전 차단한다. Gemini 안전 필터는 괴롭힘·혐오·성적·위험 콘텐츠를 `BLOCK_MEDIUM_AND_ABOVE`로 적용하고, 차단·실패 시 원문을 보존한다.
- AI 감사 로그에는 프롬프트·답변·초안을 넣지 않고 기능·상태·오류·모델·토큰·소요시간만 최대 30일 보관한다.
- 4단계 취향 리포트는 별도 AI 호출이나 스냅샷 테이블 없이 완료 기록에서 계산한다. 캘린더·평균 별점·별점 분포·Light/Core 비율·감정 TOP 3를 제공하고, 초안은 집계에서 제외한다.
- 공유는 사용자가 누른 경우에만 운영체제 공유 화면을 연다. 리포트는 요약만 공유하며 개별 기록 링크는 `전체 공개` 완료 기록에만 노출한다.
- 개별 공개 기록은 편집 라우트와 분리된 `/review/[id]` 읽기 전용 화면으로만 공유한다. 비소유자에게 저장·삭제 UI를 렌더링하지 않고, 기존 편집 링크로 접근해도 소유자 조회에 실패하면 공개 상세로 전환한다. 실제 쓰기는 계속 RLS와 소유자 조건으로 이중 제한한다.
- 계정 삭제는 데이터 내보내기 선택지를 먼저 제공하고, 이중 확인 뒤 서버 함수가 인증 사용자를 삭제해 연결 데이터를 cascade로 정리한다. 실제 계정 검증은 사용자 데이터 보호를 위해 일회용 테스트 계정에서만 수행한다.
- 클라이언트 오류 관측은 입력 본문·이메일 없이 영역·오류 종류·시간만 기기에 최대 20건 보관하며 사용자가 데이터 내보내기를 선택할 때만 포함한다.

## 가정

- 첫 사용자는 20~30대의 모바일 중심 영화 관객이다.
- 서비스명은 브랜딩 근거인 `Flick + Click`을 따라 임시로 `FLICK`라 표기한다.
- 현재 Windows 개발 환경에서는 EAS 클라우드 빌드를 사용한다.
- 초기 팀 규모는 1인 또는 소규모이며 단일 TypeScript 코드베이스의 유지비를 우선한다.

## 서비스 설정

- 독립 Git 저장소의 기본 브랜치는 `main`으로 사용한다.
- `FLICK.code-workspace`에서 프로젝트를 열고 공식 Codex 확장 `openai.chatgpt`를 권장한다.
- 배포 프로젝트와 호스팅 ID는 아직 만들지 않는다.
- 비밀정보, 환경 파일, 의존성, 캐시, 빌드 결과는 Git에서 제외한다.
